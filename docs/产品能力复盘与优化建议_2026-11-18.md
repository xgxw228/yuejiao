# 产品能力复盘：谁该读什么、谁该写什么

> 复盘时间：2026-11-18　触发点：「老师能录成绩却查不到学生成绩，得切到学生界面问」
> 结论先行：**这不是权限不足，是权限给多了 + 读侧只做了一半。**

---

## 一、先把你举的那件事说清楚

实测四条问法，同一位老师（李老师）问同样一批数据：

| 问法 | 实际结果 | 判定 |
|---|---|---|
| `张三的雅思听力多少分` | `查到张三的雅思听力成绩，分数为 6.5 分` | ✅ 正常 |
| `我班上学生成绩怎么样` | 返回 **20 条记录、全校 5 个学生**，平均 69.2 | ❌ **越权**：李老师只带张三、许明，却看到了赵敏、孙老师班上的学生 |
| `这学期有谁不及格` | `没查到具体数据，因为"不及格"这个说法太宽泛了` | ❌ 数据明明有，是说法没被识别 |
| `许明的总分多少` | `没查到许明的总分，因为系统没听出具体要查哪类数据`，还教用户改口 | ❌ 意图识别失配 |

所以真相是三层叠加：

1. **不存在权限拦截**——老师确实能查到成绩，系统没挡他；
2. **读侧只做了「单点查询」**：只认"某个学生 + 某门课"，说法一变就失配，用户体感就是"查不到"；
3. **该收的地方没收**：问"我班上"，系统返回全校——权限不是不够，是**过宽**。

一句话：这里要补的不是"给老师开放成绩查询权限"，而是**把读侧的维度补齐、把说法的口语化补齐、把数据范围收回到他名下**。

### 一个复盘时的误判，需要更正

**P0-4「学生身份可从请求体伪造」不成立。** `demo_chat_api.py` 第 116-126 行早已实现：

```python
uid = req.user_id
me = auth_service.current_user(db, req.token) if req.token else None
if me:
    if not me["features"].get("admin"):
        uid = me["id"]      # 非管理员只能用登录身份
```

我当时只看到前端传 `user_id` 就下了结论，没读这段。**唯一残留**：不带 token 调用 `/api/chat/stream` 时不校验身份——前端一定带 token，实际风险很低，但如果要堵死，可以在学生/员工 agent 上强制要求 token。

## 二、同类问题清单

### P0 · 会直接产生错数据（建议必改）

**P0-1 成绩可重复录入，无冲突校验**
- 证据：同一学生同一门课录两次，库里变成 `雅思听力 6.5` 和 `雅思听力 150.0` 两条并存；学生查这门课，平均分变成 78.25。
- 影响：老师"补录/改错"和"新增"在系统里没有区别，越录越乱，学生看到的成绩单是错的。
- 建议：改为 upsert——同 `student_id + course_name + semester` 已存在时，返回"已有 6.5 分，是否覆盖为 X"，用户确认才写。

**P0-2 分数上限 150，与业务不符**
- 证据：`录 150 分` 返回成功；`录 -20 分` 被拦住（`成绩必须在 0~150 之间`）。而雅思是 9 分制，校内课程是百分制。
- 影响：雅思录成 150 分也能过，成绩单失去意义。
- 建议：按课程前缀判断——`雅思*` 限 0~9，其余 0~100；超范围直接拒绝并说明。

**P0-3 「我班上」返回全校学生**
- 证据：见上表第 2 行。`sys_user.homeroom_teacher_id` 字段是有的（张三/许明挂李老师），但 `nl2sql_service` 里**完全没有班级/班主任维度的处理**。
- 影响：既是越权（老师看到别班学生成绩），也是语义错误（问"我班上"给全校）。
- 建议：识别"我班上/我带的学生/我的学生"→ 按 `homeroom_teacher_id = 当前登录用户` 过滤；管理员/领导才放开全校。

**P0-4 学生身份可从请求体伪造**
- 证据：`/api/chat/stream` 的 `user_id` 由前端传，后端未与 token 校验。学生端查成绩的 URL 是 `score-list?student_id={{start.user_id}}`，把请求体 `user_id` 改成 5 就能查到陈嘉怡的成绩。
- 影响：一次改包就能看同学成绩/请假记录。
- 建议：后端按 token 的 `uid` 强制覆盖 `user_id`，非管理员不得指定他人。

### P1 · 能力不对等（能写不能读 / 有身份没能力）

**P1-1 员工没有成绩查询视图**
- 现状：员工只能"问一句答一句"，没有列表、排序、筛选、导出。而录入成绩是明确的写能力。
- 建议：`GET /api/employee/scores?class=&course=&semester=&below=`，并在前端加一个"成绩册"抽屉（和请假审批抽屉同一套交互），支持按班级/课程筛、按分数排序、标红不及格。

**P1-2 家长角色形同虚设（最值得补的一条）**
- 证据：`sys_user.parent_of_student_id` 明确记录"陈女士是张三母亲"，但家长问 `我孩子这次考了多少分` → `这个我需要让顾问老师跟你确认`；问 `张三的请假批了吗` → 同样答不出。
- 影响：家长端只能问营销问题（项目、活动），跟"家长"这个身份几乎无关。需求书里家长是要看孩子学习情况的。
- 建议：客服 Agent 增加家长分支——识别到 `user_type=PARENT` 时，按 `parent_of_student_id` 只允许查：孩子成绩、孩子请假状态、孩子活动报名。这是"数据在、能力没接"的典型。

**P1-3 学生不能撤销请假**
- 现状：提交错了只能找老师驳回。
- 建议：`DELETE /api/leave/{id}`，限本人 + 状态为"待审批" + 未超过开始时间。

**P1-4 管理员有用户增删改接口，但前端没有入口**
- 现状：`user_api` 有完整 CRUD，页面上只有一个只读数据后台。
- 建议：演示用不上就删掉接口（减少攻击面）；要留就补一个简单表单。**二选一，别悬着。**

**P1-5 心理预警只能看，不能认领/跟进**
- 现状：`alert-list` 能查，NL2SQL 有 alert 的读意图，但写意图只有客户/请假/工单三类，**没有预警状态流转**。
- 影响：高危学生预警出来，没人能在系统里"接手处理"，只能口头分工。
- 建议：加 `alert-claim` / `alert-resolve`，记处理人和处理说明；领导视图能看到"未认领预警"。

### P2 · 语义理解（"查不到"的体感主要来自这里）

**P2-1 「不及格」不在意图词表**
- 证据：`这学期有谁不及格` → 判为"太宽泛"。词表里有"挂科"，但没有"不及格/低于60/没及格/补考"。
- 建议：补同义词，并把"不及格"映射为 `score < 60` 的条件，而不是要求用户说"分数"。

**P2-2 「总分」「平均分」「排名」缺失**
- 证据：`许明的总分多少` → 意图识别失败。
- 建议：`总分/合计` → `SUM(score)`；`平均分` → `AVG`（已有词但没接聚合）；`排名` → 按总分窗口排序。

**P2-3 复合条件不支持**
- 现状：一次只能带"人 + 课"两个条件。
- 建议：支持"班级 + 课程 + 分数区间 + 学期"自由组合，这也是 P1-1 表格视图天然能解决的。

**P2-4 「我班上」这类指代没有实体映射**
- 与 P0-3 同源：缺少"我/我们班/我带的学生 → homeroom_teacher_id"的映射层。

### P3 · 闭环与体验

**P3-1 成绩录入后学生无感知**
- 现状：老师录完，学生不主动查就永远不知道。
- 建议：录入时给该学生写一条站内消息/下次对话首句提示"你有一门新成绩"。

**P3-2 留资线索的负责人写死一个人**
- 证据：`build_agents.py` 里 `owner_employee_id` 固定填 3（李老师）。
- 影响：所有线上留资都堆给同一个人，其他顾问看不到。
- 建议：按轮询或按方向分配。

**P3-3 活动报名名单有接口但没人用**
- 现状：`event-registrations` 能查，前端和对话都没有入口。
- 建议：客服问"这场活动报了谁"要能答；或加"导出名单"。

**P3-4 领导没有团队视图**
- 现状：领导（郑主任）权限等同管理员，但只能进只读后台逐表翻。
- 建议：一个汇总页——今日新增线索、待审批数、未认领预警、本周活动报名数。

**P3-5 多轮指代只保留 2 轮**
- 现状：`history_hint` 只带最近 2 轮。
- 影响：连续追问第 4 轮开始丢上下文。
- 建议：放到 4 轮，超长时只保留"问"的摘要。

## 三、如果只改三件

按"投入产出比 + 用户可感知"排序：

1. **P0-1 成绩去重**（改一个 upsert，约 20 行）——不修就是错数据，最伤信任。
2. **P1-2 家长查孩子**（复用现有查询，加身份判断，约 60 行）——这是"有数据不给用"最刺眼的一处。
3. **P2-1 + P2-2 口语说法**（补词表 + 聚合，约 40 行）——直接消掉"查不到"的主要体感。

这三件做完，"老师查不到成绩""家长问不了孩子"这两类抱怨基本消失，而不用动权限模型。

## 四、我建议**不做**的

| 项 | 理由 |
|---|---|
| 给管理员补用户 CRUD 前端 | 演示不需要，留着接口反而增加攻击面；建议直接删接口 |
| 学生撤销请假 | 真实系统该有，演示场景用不上，优先级让给 P0/P1 |
| 领导/管理员拆角色 | 后台只读，领导查看属权限内合理行为，拆分只增维护成本 |
| 成绩单导出 Excel | 演示里没人会点，做了也验证不了 |

## 五、一句话总结

现在系统的能力分布是"**写得很细，读得很粗**"：每个写操作都有专门分支、参数校验、身份校验；而读操作大量依赖一句自然语言去猜，猜不中就告诉用户"换个说法"。

对演示来说，最容易加分也最容易被挑刺的，恰恰是这种"**我明明有权限、数据明明在库里，你却告诉我查不到**"的瞬间。上面 P0-1、P1-2、P2-1/2 三条，就是这类瞬间里最典型的三个。
