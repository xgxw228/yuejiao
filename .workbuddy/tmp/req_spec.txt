3. 项目概述
3.1 项目背景
「粤教服务」是一家面向国际教育 / 留学服务的企业，日常业务涉及学生管理、
销售线索跟进、留学项目咨询与活动运营等多个环节。当前业务过程中存在以下
解决的的痛点问题：
1. 人工处理效率低：学生请假、投诉反馈、客户咨询、活动报名等大量重复
性事务依赖人工逐条处理，响应慢、易遗漏；
2. 信息获取困难：公司信息、留学政策、费用标准、常见问题等分散在多份
文档中，员工与客服需要反复查找，新人上手成本高；
3. 数据分散：客户线索、学生成绩、日报、工单、报名记录分散在不同表格
中，缺乏统一管理，难以追溯与统计；
4. 用户需求复杂：不同学历、年龄、经济条件、意向的学员对留学项目需求
差异大，人工推荐主观性强、口径不一；
5. 缺少智能辅助能力：缺乏对学员情绪的持续关怀与高危预警机制，心理风
险难以及时发现与跟进。
因此，建设一套面向学生、员工、客户三类角色的智能教育服务助手系统，通过多
智能体协同，实现业务自动化、知识智能化、风险前置化。
3.2 项目定位
粤教服务智能教育服务助手系统是一款面向国际教育服务场景的多智能体智能辅助
系统。
系统主要用于：
• 信息查询（课程、活动、成绩、客户档案、政策、FAQ）；
• 辅助决策（用户画像研判与留学项目推荐）；
• 自动处理（请假申请、活动报名、日报记录、CRM 流转、NL2SQL 指令处
理）；
• 风险预警（学生心理情绪监测与高危预警）；
• 提升业务效率。
系统不用于：
• 替代人工决策（大部分的系统只是使用 AI 给出建议或者方案，具体是否采
纳需要人工决策） ；
• 执行业务审批（审批结论仍由人工确认后落库）；
• 承担专业心理 / 教育咨询责任。
4. 项目目标
4.1 总体目标
建设一个能够面向留学生、内部员工、潜在客户三类角色，通过多智能体协同提供
校园服务、业务辅助、咨询推荐与心理预警的智能化系统。

6. 系统范围
6.1 系统包含范围
系统支持：
• 用户画像研判与留学项目智能推荐（共享工具）；
• 留学生请假、心理关怀与预警、售后反馈、成绩查询；
• 员工 CRM 线索管理、日报、成绩录入、审批与 NL2SQL 指令处理；
• 客服课程 / 项目查询、课程推荐、活动查询与报名、知识库问答（公司 / 政
策 / 费用 / FAQ）；
• 对话记录沉淀与心理画像累积；
• 管理后台数据展示与系统健康检查。
6.2 系统不包含范围
当前版本不包含：
• 独立的用户登录 / 注册与完整鉴权体系（仅以 sys_user 表与 API Key 支撑
演示）；
• 线上支付与合同签署；
• 教务排课 / 考试系统的完整对接；
• 多语言客服能力；
• 移动端 App。
后续作为独立需求评估。
7. 用户使用场景
7.1 场景名称：客户咨询留学项目并获取推荐
7.1.1 场景描述
用户希望：作为潜在学员家长，输入孩子的基本情况，获得匹配的留学项目推荐及
理由。
7.1.2 输入
用户输入：「我家孩子 19 岁、高中刚毕业、想快点拿本科学历」。
7.1.3 系统处理
系统： 1. 分析输入（意图分类为「推荐项目」）； 2. 抽取结构化画像（年龄 19、
学历高中、意向升学）； 3. 调用画像研判工具进行规则匹配； 4. 计算匹配度并返
回推荐项目。
7.1.4 输出
返回：「推荐 0.5/1+2 新加坡定向培养本科班」+ 推荐理由 + 匹配度分值。
7.2 场景名称：学生倾诉情绪触发心理预警
7.2.1 场景描述
用户希望：学生表达负面情绪，系统能及时识别高危信号并通知班主任。
7.2.2 输入
学生输入：「最近压力好大，感觉活不下去了」。
7.2.3 系统处理
系统： 1. 进行情绪评估（识别高危关键词）； 2. 判定情绪分值 ≥ 70（高危）； 3.
写入预警表并记录对话； 4. 提示已通知班主任关注。
7.2.4 输出
返回：情绪标签、分值、风险等级，并提示「已通知班主任关注」。
7.3 场景名称：员工查询客户跟进记录
7.3.1 场景描述
用户希望：员工通过口语化指令查询某个意向客户的跟进记录。
7.3.2 输入
员工输入：「帮我查一下许同学的跟进记录」。
7.3.3 系统处理
系统： 1. 识别意图（查询客户）； 2. 抽取实体（客户姓名）； 3. 通过 NL2SQL 兜
底查询客户档案。
7.3.4 输出
返回：客户档案（姓名、联系方式、背景、跟进历史、状态）。
7.4 场景名称：客户报名活动
7.4.1 场景描述
用户希望：客户报名参加留学分享会等活动。
7.4.2 输入
客户输入：「我要报名留学分享会」。
7.4.3 系统处理
系统： 1. 识别意图（活动报名）； 2. 校验活动名额； 3. 写入报名记录并自动累加
报名数。
7.4.4 输出
返回：报名成功回执（含活动名称）。
7.5 场景名称：学生提交请假申请
7.5.1 场景描述
用户希望：学生提交请假申请，系统自动解析请假时间。
7.5.2 输入
学生输入：「我明天要请假一天，家里有事」。
7.5.3 系统处理
系统： 1. 识别意图（请假）； 2. 解析请假时间（明天）与时长（一天）； 3. 写入
请假申请（状态为待审批）。
7.5.4 输出
返回：请假申请记录（含起止时间、状态）
8. 功能需求
8.1 功能模块一：用户画像研判（共享工具）
8.1.1 FR-001 画像信息抽取
8.1.1.1 功能描述
系统应支持：从非结构化文本中抽取用户画像字段（年龄、学历、经济条件、意
向、语言基础、动手能力等）。第一段由 LLM 抽取，后端另提供正则关键词兜底
抽取，保证脱离 LLM 可独立测试。
8.1.1.2 输入
用户输入：结构化画像字段，或仅 raw_text 原文。
8.1.1.3 输出
系统返回：归一化后的画像字段。
8.1.1.4 业务规则
• 优先采用 LLM 抽取的结构化字段；
• 仅当未提供结构化字段时才使用正则兜底；
• 学历抽取须识别「X 毕业 / X 在读 / X 刚毕业」语境，避免把目标学历误判
为当前学历。
8.1.2 FR-002 学历归一化
8.1.2.1 功能描述
系统应支持：将自然语言学历归一化为标准桶（初中 / 高中 / 中职技校 / 专科 / 本
科 / 硕士）。
8.1.2.2 输入
用户输入：自然语言学历描述（如「高中」「大专」「研究生」）。
8.1.2.3 输出
系统返回：标准学历桶。
8.1.2.4 业务规则
• 按 硕士 → 本科 → 专科 → 中职技校 → 高中 → 初中 的优先级匹配关键词；
• 无法归一的原样返回。
8.1.3 FR-003 意向归一化
8.1.3.1 功能描述
系统应支持：将用户意向归一化为「升学 / 就业 / 移民」三类。
8.1.3.2 输入
用户输入：意向描述文本。
8.1.3.3 输出
系统返回：归一化后的意向。
8.1.3.4 业务规则
• 命中「就业 / 工作」归为就业；「移民 / 永居」归为移民；「升学 / 学历 /
本科 / 硕士 / 留学 / 深造」归为升学。
8.1.4 FR-004 规则匹配与项目推荐
8.1.4.1 功能描述
系统应支持：根据归一化画像，通过确定性规则匹配候选留学项目，输出推荐项目
与推荐理由。规则覆盖 2+2 / 0.5/1+2 / 2+2+1 / 6+6 / 9+6 / 一年制专升本 / 一年
制本升硕 / 德国双元制 等项目。
8.1.4.2 输入
用户输入：归一化画像（年龄、学历、意向、语言、动手能力等）。
8.1.4.3 输出
系统返回：候选项目列表、最优推荐（项目 + 理由 + 匹配度）、画像摘要。
8.1.4.4 业务规则
• 学历决定基础项目池（如初中 → 2+2；高中 / 中职 → 0.5/1+2；专科 → 一年
制专升本；本科 → 一年制本升硕）；
• 德国双元制须满足 18-35 岁、有德语基础、动手能力强；
• 就业导向（6+6 / 9+6）要求中职技校学历且年龄 ≥ 17；
• 无匹配结果时返回明确提示，不允许编造推荐。
8.1.5 FR-005 匹配度评分与排序
8.1.5.1 功能描述
系统应支持：对命中的候选项目计算匹配度分值并排序，意向匹配时加分。
8.1.5.2 输入
用户输入：归一化画像与命中项目。
8.1.5.3 输出
系统返回：按匹配度降序排列的项目列表。
8.1.5.4 业务规则
• 就业意向命中就业 / 双元制项目 +5 分；
• 升学意向命中本科 / 硕士 / 本硕项目 +3 分；
• 移民意向命中双元制项目 +5 分；
• 分值上限 100；
• 同一项目去重。
8.2 功能模块二：留学生智能管家（学生侧）
8.2.1 FR-006 请假申请
8.2.1.1 功能描述
系统应支持：学生提交请假申请，记录学生 ID、服务类型、起止时间、事由。
8.2.1.2 输入
学生输入：学生 ID、服务类型、起止时间、请假事由。
8.2.1.3 输出
系统返回：请假申请记录（含审批状态）。
8.2.1.4 业务规则
• 前端 / Dify 未传起止时间时，从请假事由中兜底解析（支持「今天 / 明天 /
后天」「明确日期」「半天 / 一天 / 三天」及中文数字）；
• 初始状态为「待审批」。
8.2.2 FR-007 请假查询
8.2.2.1 功能描述
系统应支持：查询请假记录，可按学生 ID、审批状态过滤。
8.2.2.2 输入
用户输入：学生 ID、状态（可选）。
8.2.2.3 输出
系统返回：请假记录列表。
8.2.3 FR-008 请假审批
8.2.3.1 功能描述
系统应支持：审批人（班主任）对请假申请进行通过 / 驳回操作。
8.2.3.2 输入
审批人 ID、是否通过（布尔）。
8.2.3.3 输出
系统返回：审批结果（已通过 / 已驳回）。
8.2.3.4 业务规则
• 申请不存在时返回 404；
• 审批结论仍由人工确认后落库。
8.2.4 FR-009 情绪评估
8.2.4.1 功能描述
系统应支持：对学生输入进行情绪评估，输出情绪标签、分值、风险等级，并沉淀
对话记录、更新心理画像。
8.2.4.2 输入
学生 ID、文本内容（可附带 LLM 的情绪标签 / 分值）。
8.2.4.3 输出
系统返回：情绪标签、情绪分值、风险等级、是否预警、提示语。
8.2.4.4 业务规则
• 未提供情绪字段时用关键词兜底评估；
• 高危关键词（自杀、想死、活不下去等）计 90 分；负面关键词（焦虑、抑
郁、失眠等）计 55 分；积极关键词计 15 分；默认平稳 20 分。
8.2.5 FR-010 心理画像管理
8.2.5.1 功能描述
系统应支持：维护学生的长期心理画像（最新情绪标签、分值、最近交互时间、历
史情绪波动），并支持按学生查询。
8.2.5.2 输入
学生 ID。
8.2.5.3 输出
系统返回：心理画像（含解析后的历史情绪 JSON）。
8.2.5.4 业务规则
• 每名学生唯一画像，采用 upsert 方式维护；
• 历史情绪以 JSON 数组保存，仅保留最近 50 条。
8.2.6 FR-011 心理预警
8.2.6.1 功能描述
系统应支持：当情绪分值达到高危阈值时，自动写入预警记录并通知班主任；支持
查询预警列表与更新预警状态。
8.2.6.2 输入
学生 ID、情绪分值；查询条件（状态）、预警状态更新。
8.2.6.3 输出
系统返回：预警记录 / 预警列表 / 更新结果。
8.2.6.4 业务规则
• 分值 ≥ 70 → 高危，写预警表 + 通知班主任；
• 40 ≤ 分值 < 70 → 关注，仅累积画像，不强制预警；
• 分值 < 40 → 正常。
8.2.7 FR-012 售后反馈提交
8.2.7.1 功能描述
系统应支持：学生提交售后反馈 / 投诉，生成工单。
8.2.7.2 输入
学生 ID、反馈内容摘要、详情（可选）。
8.2.7.3 输出
系统返回：反馈工单记录（初始状态「待处理」）。
8.2.8 FR-013 售后反馈查询
8.2.8.1 功能描述
系统应支持：查询反馈工单，可按学生 ID、状态过滤。
8.2.8.2 输入
学生 ID、状态（可选）。
8.2.8.3 输出
系统返回：反馈工单列表。
8.2.9 FR-014 工单解决与通知
8.2.9.1 功能描述
系统应支持：解决工单并标记已通知学生。
8.2.9.2 输入
解决方案。
8.2.9.3 输出
系统返回：解决结果。
8.2.9.4 业务规则
• 工单不存在时返回 404；
• 解决后状态置为「已解决」、is_notified=1。
8.2.10 FR-015 学生成绩查询
8.2.10.1 功能描述
系统应支持：学生查询本人成绩。
8.2.10.2 输入
学生 ID。
8.2.10.3 输出
系统返回：成绩记录列表。
8.3 功能模块三：员工业务助手（员工侧）
8.3.1 FR-016 意向客户录入

9. 业务规则
9.1 画像研判规则
当：系统获得归一化画像。 系统应该：按学历确定基础项目池，再结合年龄、语
言、动手能力、意向进行匹配与加分，输出可解释的推荐理由与匹配度。
9.2 心理预警阈值规则
当：情绪分值达到阈值。 系统应该：
• 分值 ≥ 70 → 高危，写预警表 + 通知班主任；
• 40 ≤ 分值 < 70 → 关注，仅累积画像；
• 分值 < 40 → 正常。
9.3 客户状态流转规则
当：员工更新客户状态。 系统应该：仅允许「新增意向 / 跟进中 / 已签约 / 已流
失」四种状态之一，否则拒绝并提示。
9.4 活动报名名额规则
当：客户报名活动。 系统应该：校验当前报名人数是否达到上限，已满则拒绝报
名；成功后报名数 +1。
9.5 默认处理规则
当用户输入信息不足： 系统应该：
• 请求补充信息（如画像缺失年龄 / 学历时提示补充）；
• 返回默认结果（如请假未传时间时按事由兜底解析）；
• 给出提示（如未匹配到项目时给出明确说明）。
9.6 数据不足规则
当系统无法获得有效信息： 系统：
• 不允许编造结果；
• 明确提示信息不足；
• 必要时建议人工处理。

11. 异常处理需求
11.1 外部服务异常
当：第三方服务（LLM 模型 / 知识库检索）不可用。 系统：
• 尝试备用方案（如情绪评估、画像抽取降级为正则关键词兜底）；
• 返回降级结果；
• 提示用户。
11.2 数据查询失败
系统：
• 尝试其他来源（如请假时间解析失败时回退到默认）；
• 无结果时明确说明（如「未找到该客户」「未匹配到合适项目」）。
11.3 系统异常
要求：
• 隐藏内部错误；
• 返回用户可理解提示；
• 参数不合法返回 400，资源不存在返回 404，请求体校验失败返回 422。
12. 安全需求
12.1 数据安全
系统必须：
• 防止非法修改（状态流转、审批等关键字段需经接口校验）；

13. 非功能需求
13.1 性能需求
系统应：
• 支持学生、员工、客户三类用户并发访问（演示级）；
• 保证响应速度（规则匹配、SQLite 查询为本地毫秒级）；
• 避免重复计算（心理画像采用 upsert、情绪历史仅保留最近 50 条）。
13.2 可用性需求
系统：
• 单点故障不能导致整体不可用（前端 / Dify / 后端分层解耦，后端与知识库
问答可独立降级）；
• 支持异常恢复（SQLite 首次启动自动建库并写入种子数据）。
13.3 可维护性需求
系统支持：
• 功能扩展（新增路由 / 规则条目）模块升级（规则引擎与接口解耦）；
• 数据更新（知识库文档、课程 / 活动数据可更新）。
• 举例： 如果你的代码 没有任何注释，这种代码可维护性就不高。
13.4 可扩展性需求
未来支持：
• 新业务（新 Agent、新服务类型）；
• 新数据（新表 / 新知识库）；
• 新接口（新增自定义工具）。
• 方便新增功能（开闭原则：对修改关闭，对扩展开放）；
13.5 易用性需求
要求：
• 操作简单（口语化指令、拟人化对话）；
• 无需学习复杂规则；
• 输出易理解（中文话术、Markdown 表格、明确的推荐理由）。

16. 业务边界
明确： 系统可以：
• 提供课程 / 活动 / 成绩 / 客户档案等信息查询；
• 通过规则引擎输出可解释的项目推荐；
• 自动记录请假、报名、日报、CRM、预警等业务数据；
• 识别学生高危情绪并预警。
系统不能：
• 替代人工做最终审批决策；
• 替代专业心理 / 教育咨询，承担专业责任；
• 在数据不足时编造结果；
• 承担线上支付、合同签署等金融 / 法律行为。
